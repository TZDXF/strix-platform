# 围绕 Strix 构建内部安全测试平台 —— 可行性规划

> 版本：v0.3（决策已锁定）｜日期：2026-08-14
> 目标读者：安全/平台团队、立项决策者

---

## 0. 已锁定的范围决策（2026-08-14）

| # | 决策项 | 结论 | 影响 |
|---|--------|------|------|
| 1 | 测试地址 | **由用户提供，平台不负责部署项目** | 砍掉原 Phase 2 自动部署（最大工程量项）；平台核心流程简化为"获取源码 → 扫描 → 报告" |
| 2 | LLM | **走公司统一网关**（`LLM_API_BASE` 接入 OpenAI 兼容网关） | 密钥收口、可审计可限流；成本由网关侧统计 |
| 3 | 基础设施 | **不提供独立服务器**，与其他内网服务共用现有主机 | 安全隔离必须全部在 Docker 网络层解决，成为本平台**第一风险项**（见 5.2） |
| 4 | 提交权限 | **暂不做权限体系** | 不做 SSO/RBAC，但必须保留最低成本护栏（共享访问令牌 + 审计日志，见 5.4） |
| 5 | 审批与预算 | **平台不做审批流程，不设预算上限** | 扫描档位（quick/standard/deep）全开放；成本治理移交公司 LLM 网关侧；平台仅做成本透明展示与任务超时回收（见 5.3） |
| 6 | 技术选型补充 | **对象存储 RustFS，前端 Vue 3** | RustFS 为 S3 兼容存储，代码层统一走 S3 API（boto3），后端可替换；报告下载建议经 API 代理或验证 presigned URL 行为 |
| 7 | 模型策略 | **只允许 free 档模型，失败自动重试** | 网关 `free` 别名有间歇性故障（Phase 0 实测 503 后数分钟自愈，路由至 deepseek-v4-flash）；worker 必须实现 LLM 连接失败级重试（实测 1 次尝试成功） |

## 1. 结论（TL;DR）

**可行，且范围收缩后 MVP 即完整产品形态。**

Strix 是 CLI 优先、headless 友好、产物完全落盘结构化的 AI 渗透测试引擎（`strix -n` 非交互模式、退出码语义明确、SARIF/PDF/JSON 报告齐备），平台化封装是低风险工程。

**由于"不部署 + 无独立服务器"，项目的关键风险从工程量转移到了网络隔离**：目标地址由用户提供（通常是内网测试环境），strix 会向其发送真实攻击流量。在一个共享内网主机上，必须做到**每个扫描任务的出网流量只能到达"它自己的目标 + 公司 LLM 网关"**，否则平台会变成一台"谁都能用的内网攻击跳板"。这是架构上的硬性要求，不是优化项。

**前置条件（Phase 0 决策门）不变**：先手工跑通 strix 对 2~3 个内部典型应用的扫描，实测**发现质量、耗时、单次成本**，并在"受限出网"条件下验证 strix 功能是否退化。指标不达标不立项。

## 2. 需求场景（修订后）

| 角色 | 行为 |
|------|------|
| 团队开发者 | 提交：代码仓库地址（git URL）或压缩包（zip），**可选**附一个已部署的测试地址（URL） |

内网部署、内部使用，不做对外服务，暂不做用户权限体系（保留最低护栏，见 5.4）。

## 3. Strix 引擎能力评估（基于源码/文档核实）

### 3.1 与平台化直接相关的核心事实

| 能力点 | 核实结果 | 对平台的意义 |
|--------|----------|--------------|
| 目标类型 | 本地目录 / git 仓库 URL / Web 应用 URL / 域名 / IP / API 规范文件（OpenAPI/Swagger、Postman），支持 `-t` 多目标组合 | 白盒（源码）+ 黑盒（用户提供 URL）联合扫描原生支持；API 规范测试可作增强项 |
| 非交互模式 | `strix -n --target ...`；退出码：0 无漏洞 / 1 执行错误 / 2 发现漏洞 | 可直接作为任务子进程调用并判定结果 |
| 扫描模式 | quick（分钟级）/ standard（30min~1h）/ deep（1~4h，默认） | 三档全开放、用户自选（决策 #5），表单默认 quick |
| 产物落盘 | `strix_runs/<run-name>/`：`run.json`、`vulnerabilities.json`、`vulnerabilities.csv`、`vulnerabilities/<id>.md`、`penetration_test_report.md`、SARIF、PDF | 平台解析 JSON 入库渲染报告页，MD/PDF 原样归档下载 |
| 漏洞结构化字段 | id、title、severity、cvss、cwe、cve、endpoint、evidence、impact、poc_script_code、code_locations（含 fix_before/fix_after diff）、remediation_steps、fix_effort | 报告页/趋势统计/修复建议可直接渲染 |
| 成本控制 | CLI 提供 `--max-budget-usd`（单次扫描美元上限）；内部有 token 预算执行与上下文压缩机制 | 平台不设预算上限（决策 #5），治理移交网关侧；超时仅用于回收 worker 资源 |
| 配置方式 | 环境变量（`STRIX_LLM`、`LLM_API_KEY`、`LLM_API_BASE`、`STRIX_TELEMETRY` 等）> `~/.strix/cli-config.json` > 默认值 | 全部环境变量注入，无交互配置，适合容器化 worker |
| 沙箱 | Kali Linux Docker 容器，内置全套渗透工具（nuclei、sqlmap、ZAP、semgrep、katana、nmap、trivy、Caido、Playwright 等），首次运行自动拉镜像 | Agent 攻击行为限制在容器内；**网络出向隔离必须由平台补**（见 5.2） |
| 自定义技能 | `/opt/strix-skills` 可注册自定义 skill，覆盖内置行为 | 可注入企业安全基线（后期增强项） |
| 遥测 | `STRIX_TELEMETRY` 环境变量可关闭 | 部署时显式关闭，满足内网合规 |
| 许可证 | Apache 2.0 | 内部使用、二次开发无法律障碍 |
| LLM 接入 | LiteLLM 统一层；`LLM_API_BASE` 支持 OpenAI 兼容网关 | **直接对接公司统一网关**，天然匹配决策 #2 |

### 3.2 引擎侧风险（已在社区/源码中核实）

| 风险 | 证据 | 对策 |
|------|------|------|
| **Token 消耗大**是已知痛点 | Issue #928：工具输出反复进入上下文导致 token 成倍增长；官方缓解建议就是 `--max-budget-usd` + quick/diff 模式 | 平台不设限（决策 #5），成本治理在网关侧（配额/告警/限流）；任务超时仅回收资源，非成本手段 |
| 长任务稳定性问题偶发 | Issue #927：CI 运行因 Caido 引导竞态 + LLM 不可达挂起（已修复） | 固定版本；worker 级超时强杀；失败可重试 |
| 项目年轻、迭代快，内部 API 不稳定 | 高频提交，模块结构持续变动 | 集成方式锁定为"CLI 子进程 + 产物文件解析"，绝不 import 内部模块；版本 pin + 升级验证流程 |
| LLM 结果非确定性 | Agent 机制天然属性 | 报告页标注"AI 辅助测试结果，需人工复核" |

                           │
┌──────────────────────────▼────────────────────────────────────┐
│  API 服务（FastAPI）                                            │

### 每个扫描任务的网络隔离（共享主机上的硬性要求）

```
 共享内网主机
 ├─ 平台服务（api/redis/pg/rustfs/frontend）─── 正常内网访问
 │
 └─ 任务执行时临时创建 ── task-<id> 专用 docker network（bridge）
      ├─ Strix 沙箱容器（Kali，攻击行为发生地）
      └─ 出向规则（宿主机 DOCKER-USER / iptables 按源网络过滤）：
          ✓ 目标 URL 的 host:port（本任务用户填写的那个）
          ✓ 公司 LLM 网关（若 CLI 侧代理需要经此网络）
          ✓ 内部包管理镜像（构建 PoC 依赖时）
          ✗ 其余一切内网网段、公网、云元数据地址（169.254.169.254 等）
```

分工细节：

- **LLM 调用**发生在宿主机上的 strix CLI 进程（Agent 编排层），不经过沙箱容器网络——宿主机出向只需放行公司 LLM 网关。
- **攻击流量**发生在沙箱容器内，经任务专用网络出向——只允许到本任务的目标 URL。
- 目标 URL 在提交时解析 host（支持域名/CIDR 白名单二次确认），扫描结束删除该 network 与 iptables 规则。
- Phase 0 必须实测：出向受限后 strix 的功能退化情况（nuclei 模板更新、Interactsh 带外检测等依赖外网的能力可能不可用，需评估是否可接受或定向放行）。

## 5. 关键技术问题与对策（修订后）

### 5.1 用户提供的测试地址（取代原"自动部署"章节）

平台不部署，但要对用户填写的 URL 做约束与校验：

1. 仅接受 `http(s)`，且**必须是内网测试环境域名/IP**——维护一个目标允许清单（如 `*.test.xxx.internal`、指定网段），不在清单内的目标需管理员临时批准（Phase 0 就定好清单初值）。
2. URL 是可选项：只提交源码 → 纯白盒扫描；源码 + URL → 白盒 + 黑盒联合（`strix -n -t <src> -t <url>`）。
3. 明确告知用户：黑盒扫描会向该地址发送真实攻击流量，必须是本人负责的测试环境（提交时勾选确认）。

### 5.2 共享主机上的网络隔离（第一风险项）

没有独立服务器兜底，隔离必须在 Docker 层做严：

| 层 | 措施 |
|----|------|
| 任务网络 | 每任务独立 bridge network；扫描结束即销毁 |
| 出向过滤 | 宿主机 `DOCKER-USER` 链按源网络匹配，白名单只含：本任务目标、LLM 网关、内部包镜像；显式 deny 内网保留网段与管理网段、云元数据地址 |
| 资源限制 | 沙箱容器 CPU/内存 limits，防资源耗尽影响同机其他服务 |
| 兜底 | 平台主机自身的防火墙规则只放行业务必需端口；定期审计 iptables 规则与任务 network 残留 |

残余风险需管理层知悉并签字：共享主机上运行攻击性工具，若隔离配置失误，影响面是整个内网。缓解手段已列，但**无法达到独立服务器/VLAN 级别的隔离强度**。

### 5.3 成本治理（平台不审批、不设上限）

按决策 #5，平台不做审批流、不设预算上限，治理责任这样划分：

| 层 | 职责 |
|----|------|
| 公司 LLM 网关 | **成本治理主战场**：服务 Key 配额、超额告警/限流、月度账单。建议平台上线前在网关侧完成配置 |
| 平台 | 只做**透明**不做**强制**：解析 run 产物中的 usage 数据，在报告页展示单任务成本，供团队自查与网关对账 |
| 任务超时 | 仅用于回收 worker 资源（防僵尸任务占用共享主机），不是成本控制手段。**Phase 0 实测修正**：quick 模式在"源码+URL"双目标上耗时 77 分钟（远超官方"分钟级"宣传），建议默认 quick 2h / standard 4h / deep 8h |

扫描档位三档全开放（quick/standard/deep），用户提交时自选。Phase 0 仍需实测各档位成本——不是为了设限，而是为网关配额参数和用户预期提供数据。

### 5.4 最低成本护栏（暂不做权限体系的前提下)

即使不做 SSO/RBAC，以下三项不可省——否则平台等于一台无鉴权的"内网攻击即服务"：

1. **共享访问令牌**：一个全员共用的 Bearer Token，够拦住无关人员/扫描器，成本几乎为零。
2. **全量审计日志**：谁（内网 IP + 令牌）、何时、提交了什么目标——出事后可追溯。
3. **目标允许清单**（见 5.1）：即使令牌泄露，攻击面也被限制在测试环境网段内。

### 5.5 集成方式（防引擎版本漂移）

- Worker 通过**子进程调用 strix CLI**，不 import 其 Python 内部模块。
- 解析产物只依赖落盘文件契约：`run.json`、`vulnerabilities.json`（字段见 3.1）。
- strix 版本 pin（Phase 0 实测基线：`pip install strix-agent==1.5.3`）；升级走"版本验证任务"（对标准靶场跑 quick 比对结果）后再全量。
- 兜底：JSON 解析失败时原始 run 目录整体归档 RustFS，MD/PDF 始终可下载。

## 6. 分期实施路线（修订后：MVP 即完整产品）

### Phase 0 —— 引擎与隔离验证（1~2 周）★立项决策门

手工执行，不写平台代码：

1. 准备目标：2~3 个内部典型应用（源码 + 已部署测试 URL）+ 1 个标准靶场（OWASP Juice Shop / DVWA）。
2. 每目标跑 quick / standard 两档，记录：**发现漏洞数与真实性（人工核验误报）、墙钟时间、单次成本**（经公司 LLM 网关统计）。
3. **受限出网实测**：手工搭建"任务专用 network + DOCKER-USER 白名单"，验证 strix 在该条件下能否正常工作、哪些能力退化（nuclei 模板更新、Interactsh 等）。
4. 验证 `vulnerabilities.json` 解析、退出码行为、run 产物中 usage/成本数据的可得性（供报告页成本展示）。
5. 产出《引擎验证报告》（含成本实测数据与超时参数建议值，供网关配额与用户预期参考）+ 立项 Go/No-Go。

### Phase 1 —— MVP（3~4 周，即完整产品形态）

- 提交页：git URL / zip 上传 + 可选测试 URL（允许清单校验）+ 扫描档位（三档全开放，默认 quick）+ 共享令牌校验。
- 任务流水线：入队 → 获取源码（防穿越/炸弹/体积上限）→ 按第 4 节隔离方案创建网络 → `strix -n -t src [-t url] --scan-mode <m>` → 解析入库 → 销毁网络与环境。
- 报告页：漏洞列表（按严重级别排序）、详情（PoC、代码位置、修复建议 diff）、原始报告（MD/PDF/SARIF）下载、任务状态与实时日志。
- 运营基础：任务超时回收、失败重试、并发上限（共享主机建议 ≤2）、企业微信/钉钉/飞书完成通知、单任务成本展示（usage 数据 + 网关对账）。
- 部署：Docker Compose 单机（api / worker / redis / postgres / rustfs / frontend），`STRIX_TELEMETRY=off`。

### Phase 2 —— 加固与效率（按需，2~3 周）

- 漏洞去重与趋势（同一仓库跨次扫描 diff：新增/修复）。
- 通知增强：发现高危及以上立即告警安全团队。
- strix 版本升级验证流水线。
- 自定义 skills 注入公司安全基线（如内部 API 审计规范）。

### Phase 3 —— 企业化（远期，按需）

SSO/LDAP + RBAC（原决策"暂不做"，预留）、成本看板（如届时需要配额/审批，另行决策）、Git webhook（PR 触发 quick + `--scope-mode diff`）、合规格式报告导出。

## 7. 技术选型

| 层 | 建议 | 理由 |
|----|------|------|
| 后端 | Python + FastAPI | 与 strix 同生态，工具链复用 |
| 任务 | Celery + Redis | 成熟够用；后期可换 K8s Job |
| 数据库 | PostgreSQL | 任务/漏洞/成本元数据 |
| 对象存储 | RustFS（S3 兼容） | run 产物归档；平台代码统一走 S3 API（boto3），存储后端可替换；部署时验证 presigned URL 行为（报告下载） |
| 前端 | Vue 3 + Vite | 报告渲染为主 |
| 部署 | Docker Compose 单机（共享主机上的独立 compose 项目） | 与同机其他服务网络隔离（平台自身网络与任务网络分开） |
| LLM | 公司统一网关，`LLM_API_BASE` + `LLM_API_KEY`（网关侧签发的服务 Key） | 决策 #2；模型选择以 Phase 0 实测效果为准（官方推荐 GPT-5.4 / Claude Sonnet 4.6 / Gemini 3 Pro 档位，经网关需确认有同级模型） |

## 8. 风险清单（修订后）

| # | 风险 | 等级 | 缓解 |
|---|------|------|------|
| 1 | **共享主机上攻击流量失控**（隔离配置失误 → 影响整个内网） | 高 | 任务级专用网络 + DOCKER-USER 白名单 + 目标允许清单 + 规则审计；残余风险需管理层知悉（5.2） |
| 2 | 引擎实测效果/成本不达预期 | 高 | Phase 0 决策门 |
| 3 | LLM 成本失控（平台不设限，依赖网关治理） | 高 | 网关侧配额/告警/限流；报告页成本透明展示；并发上限收窄同时失控面 |
| 4 | 受限出网下 strix 功能退化 | 中 | Phase 0 专项实测，必要时定向放行（仅安全工具更新源） |

## 附录 A：Strix 关键集成契约（已按 strix 1.5.3 实测核实）

```bash
# Worker 侧标准调用形态（CLI 无 --run-name 参数，run 目录名自动生成，
# Worker 需通过"扫描前后目录快照 diff / 最新 run.json mtime"定位本次产物目录）
STRIX_LLM="<gateway-model>" \
LLM_API_KEY="<网关签发的服务Key>" \
LLM_API_BASE="https://llm-gateway.company.internal/v1" \
STRIX_TELEMETRY=off \
strix -n \
  -t /workspace/task-123/src \                  # 白盒：源码目录（必选）
  -t https://app-x.test.company.internal \      # 黑盒：用户提供的测试地址（可选）
  -m standard                                   # quick | standard | deep
# 退出码: 0=无发现  1=执行错误  2=发现漏洞
# 产物: <cwd>/strix_runs/<auto-name>/{run.json, vulnerabilities.json,
#        vulnerabilities.csv, vulnerabilities/*.md,
#        penetration_test_report.md, *.sarif, *.pdf}
# run.json 内含 llm_usage（requests/tokens/按agent分解）；自定义网关模型
# 的美元成本估算可能为 0，成本以网关账单为准
```

其他实测确认的 CLI 能力（平台可择机采用）：

- `-t` 还接受 **API 规范文件**（OpenAPI/Swagger `.json/.yaml`、Postman collection 导出或 `postman://<id>` 直连）——用户可提交 API 规范做针对性测试，建议列入 MVP 后的增强项。
- `--max-turns N`：每 agent 轮次上限（默认 500），可作为失控护栏（非预算手段）。
- `--resume <RUN_NAME>`：断点续扫，长任务失败恢复可用。
- `--instruction` / `--instruction-file`：提交表单可开放"测试重点说明"字段透传。
- 本地目录会被**可写挂载**进沙箱——平台侧源码目录必须按任务隔离放置。
